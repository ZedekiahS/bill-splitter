# 自建后端与国内部署

当前运行链路：浏览器 → 同源 Node.js API → PostgreSQL。正常登录、账本、邀请、还款和收据不再调用 Firebase、Rosefire 或 Google CDN。保留原有前端与中英切换。此文说明部署配置；仓库更新不会自动部署到公网。

## 本地启动

需要 Node.js 22+（本机使用 24）、PostgreSQL（本机验证 18）。首次 `npm ci`，复制 `.env.example` 为 `.env`，填写数据库连接，然后：

```powershell
npm run db:migrate
npm start
```

打开 `http://127.0.0.1:2801/index.html` 注册。账号、账本和文件存在数据库，浏览器只保留会话 Cookie 和界面偏好。`?demo=1` 是独立的本地体验数据，不能跨设备共享，也不会自动导入账号。

本工作站为本项目创建了独立集群 `.local/postgres`，仅监听 `127.0.0.1:55432`；未修改原有 5432 服务。数据库为 `bill_splitter` 和 `bill_splitter_test`。连接保存在被 Git 忽略的 `.env` / `.env.test`，不要上传。若重启电脑后数据库未运行，在仓库目录执行：

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\pg_ctl.exe' -D '.local/postgres' -l '.local/postgres.log' -o '-p 55432 -h 127.0.0.1' start
```

## 服务器配置

部署在国内云主机和同区域 PostgreSQL 即可，运行时不依赖境外身份服务。域名、云主机和数据库需要实际开通；本次未开通付费资源，也未执行公网发布。

1. 使用独立数据库和非超级用户的应用账号，只允许应用服务器连接；数据库不直接开放公网。托管数据库按厂商要求启用 TLS、校验证书，不关闭证书校验。
2. 安装 Node.js 24 LTS，上传代码，执行 `npm ci --omit=dev`。配置由服务器私密环境文件或密钥管理服务提供，文件权限只给运行账号。
3. 设置 `NODE_ENV=production`、`PUBLIC_ORIGINS=https://实际域名`、`TZ=Asia/Shanghai`、`HOST=127.0.0.1`、`PORT=2801` 和 `DATABASE_URL`。生产模式拒绝 HTTP 的公开来源。
4. 执行 `npm run db:migrate`，用 systemd 等进程管理器运行 `node server/start.mjs`，配置开机启动和故障重启。环境变量需要传入进程，不能只留在交互终端。
5. 用 Caddy/Nginx 提供 HTTPS；`deploy/Caddyfile` 是同机 Caddy 示例。Caddy 环境变量 `APP_DOMAIN` 填实际域名。数据库和 2801 端口保持内网/回环访问，只公开反向代理的 80/443。
6. 若要恢复真实客户端 IP，`TRUST_PROXY` 只填写实际受信代理地址/网段，例如同机代理 `127.0.0.1`，不可设置成信任任意来源。限流依赖此 IP。
7. 公网开放前补齐邮箱验证、密码找回投递、服务条款和隐私告知，并按实际运营主体、域名、地区与业务核对备案等上线要求。当前不把“具备部署代码”当作“已可无条件公开运营”。

提供 Dockerfile 作为替代打包方式：构建 `docker build -t bill-splitter .`，先用同一镜像运行 `node server/migrate.mjs`，再启动服务。生产环境变量从部署系统注入；宿主机只映射 `127.0.0.1:2801:2801`，容器内 `HOST=0.0.0.0`。容器的数据库主机名应指向可达的内网数据库，不能直接照抄宿主机回环地址。本次未在此 Windows 工作站执行容器构建或公网 HTTPS 部署。

## 身份、事务与文件

- 邮箱 + 密码为第一阶段登录方式。密码用带随机盐的 scrypt 保存；服务端保存会话令牌摘要，浏览器 Cookie 为 HttpOnly、SameSite=Lax，生产加 Secure 与 `__Host-` 前缀。会话七天到期，退出会立即撤销。
- 邮箱目前只是登录标识，`verified=false`，尚未证明邮箱归属。没有可用的邮件找回入口；不按邮箱或昵称自动合并任何账号。
- 内部用户 UUID 与 `bs_identities` 的登录身份分开。后续微信、QQ、+86 登录需要真实提供方配置、回调校验与已登录账号的绑定验证；当前没有空壳第三方按钮，也没有假定绑定已完成。
- 服务端从 Cookie 取得身份，不接受客户端自报的 owner UID。成员审批、收款人权限、分摊计算及日期校验都在服务端执行。
- 每个账本是一个 JSONB 事务单元，修改时锁定对应行；独立的成员索引用于查找访问范围。适合当前小组账本规模，大账本需要测量后再分页/拆表。
- 写操作带幂等键，服务端存储结果；同一次请求重试不会重复记账。客户端在当前页面的网络/服务错误后保留原键，不自动重试金钱记录。关闭或重载页面后应先核对账本再重新录入。
- 收据二进制存放在私有数据库表，只有账本成员可下载，不生成公开文件链接。每份最多 200 KB、每笔最多三份。备份数据库即包含附件；后续可迁移到国内私有对象存储。
- 周期账单仍在打开/刷新账本时计算待确认项，不是后台自动扣款。以 Asia/Shanghai 作为本阶段账期时区。

## 备份与维护

使用数据库服务的自动备份；自管 PostgreSQL 可用 `pg_dump --format=custom --file=backup.dump` 配合私密 PG 环境变量/密码文件。备份含个人资料、账单和收据，应加密并限制访问，定期在独立数据库用 `pg_restore` 演练恢复。不要把连接密码写进仓库或日志。

迁移前先备份。`db:migrate` 当前只创建 v1 表结构，事务内执行，不清空业务数据；今后变更需要新增迁移。定期清理过期 `bs_sessions` 和 `bs_auth_limits`；不要随意删除 `bs_requests`，否则失去对应历史请求的防重保障。

旧 Firebase 数据和浏览器体验数据均未自动迁移。旧代码、规则保留供历史参考；主服务不提供旧 HTML 页面和 Firebase Hosting 配置入口。若之后需要导入旧账单，先导出、确认账号映射并单独验证导入，不按昵称猜测归属。
