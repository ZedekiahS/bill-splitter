# 冲突核对、全额收款恢复与首次分摊转换

修复 `4be1d9c` 复核发现的三项 P2 和一项 P3，不增加新的业务模块。

## 行为

- 组合冲突后，即使名称和成员改回旧值，也保留旧基准版本。重复草稿捕获、切换、恢复都不会自动接受远端版本。明确“已核对，保留我的编辑”才可采用最新版本提交；放弃修改则展示并保留远端最新名称和成员。
- 账单详情独立显示当前账号的“核实上次收款”入口，不依赖剩余欠款或待结清列表。全额收款成功但回复丢失后，关闭弹窗、重载，再从账单详情核实，仍使用原请求和幂等键；确认成功后入口消失。其他账号不显示该账号的待核实操作。
- 分摊转换遵循明确规则：已有手工总额时优先恢复它，首次进入按金额用该总额初始化份额；已经编辑过的按金额份额保持原样。没有手工总额时，从有效项目合计初始化金额和项目参与人，首次按金额也沿用该次项目计算的份额。未完成的项目不会被当成有效转换来源。连续下一笔仍清空金额。
- 更新已被删除的组合返回可恢复的 409 与“已删除”提示，接入已有的删除状态界面，保留本地编辑并允许明确放弃。真正无权修改现有组合仍返回权限错误。

## 验证

1. 在修改前运行真实编辑器 DOM/事件回归，确认冲突后的基准从 1 漂移到 2、纯逐项切出金额变空、200 元总额混入 100 元份额、删除后错误提示等失败。
2. 收款回归运行实际页面渲染函数、API 客户端、提交状态与账本逻辑，确认旧版零余额详情没有核实入口；修复后部分和全额收款均可在模拟重载后从详情继续核实，且操作对账号隔离。
3. `npm test`：16 个测试文件，232 项通过。随后单独重跑收款导航的 12 项，新增账号隔离断言通过。
4. PostgreSQL API：57 项通过。沿用隔离的 `entry_regression_20261106` schema，不清空手机账本。三账号下覆盖部分 50 元及全额 100 元，各自模拟发送前断网、提交后丢回复、回复解析失败、服务错误；连续失败两次并模拟重载后重试，每次只保留一条流水，剩余分别为 50 元和 0 元。
5. 多账号删除组合后直接更新，返回 409 和删除提示；无权编辑仍为 403；三个账号的组合状态一致。

原来的 100 元、60/40 来回切换、未完成项目分配、多个组合草稿、停用成员保留、明确冲突确认等测试继续通过。代码和中英文消息检查通过。

本轮使用真实 HTML/DOM 事件和受控收款页面函数、实际 PostgreSQL 服务，没有重新进行真实浏览器视觉或手机验收，也没有公开部署。关闭整个标签页或会话存储被禁用时的恢复限制维持上一轮说明。
