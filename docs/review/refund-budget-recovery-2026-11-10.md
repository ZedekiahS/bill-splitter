# 退款、批量收款与预算恢复收尾

基于 `1b38a77` 分析复核中报告的五个问题。本轮不扩展功能，不加入押金。

## 修复

1. **批量收款与返还的未知结果**：结算页使用已有 `paymentSubmission`，冻结原始金额、付款方向、日期、备注、抵扣分配及版本和请求键。请求开始即保护输入；关闭重开或刷新标签页仍核实原请求。即使已经全额结清，结算页也保留待核实入口。服务端未收到原请求且期间账目变化时，原请求返回冲突，用户核对最新明细后才能发起新请求。
2. **合法多付状态的备份恢复**：取消“累计还款不得超过原份额加有效返还”的错误上界。当前双向金额继续严格核对有效付款流水，撤销关联、退款容量、成员引用仍校验；历史版本按实际记录过的对应方向转账总量校验上界，而不按目前有效转账或原消费份额截断。不会删除历史或修改金额来让导入通过。
3. **退款核实显示**：提交开始即锁定金额、日期、条目、受益份额和备注。待核实状态从冻结载荷还原所有这些字段及收款人，避免显示 30 元却实际核实 20 元。
4. **预算内部区域重建**：当前个人报告登记预算区域更新回调。旧请求结束时只刷新当前挂载的预算区域，覆盖分类、币种、概览/历史切换和页面往返。成功刷新预算，失败保留输入并恢复可操作的核实入口。
5. **未提交日期保护**：已加载报告不再因为旧预算请求完成而整体重绘。返回后新输入的日期、焦点保持不变；如果返回页还停在被旧请求失效的加载状态，仍重新发起报告读取。

## 可运行验证

- `npm test`：**300 项通过**。
- 两个 API 测试文件在独立 PostgreSQL schema 中串行运行：**71 项通过**。schema 测后移除，没有清空用户账本。
- 新测试先在原实现运行：批量未知结果未冻结、退款等待期间可编辑、合法备份被拒绝、预算当前表单无法恢复、日期输入被替换均能触发失败；修复后转为通过。

### 真实服务端和 PostgreSQL

- 三个虚构账号经注册、邀请、认领加入同一账本；分别读取并核对完整账单和资金流水。
- 实际批量窗口函数、DOM 表单事件、API 客户端及数据库链路，分别覆盖普通还款/反向返还，以及请求发送前失败/提交成功后响应丢失。关闭重开后核实原请求、载荷与键保持一致；额外成员在期间记款也不会把核实变成新收款。每个场景最终只新增一笔 40 元，反向返还剩余 60 元。
- 退款表单提交 20 元，等待真实数据库提交后模拟修改为 30 元，再丢弃响应。核实显示还原为 20 元及原备注，第二次请求与第一次相同；三个账号都只看到一笔 20 元退款。
- B 原承担 300 元：还款 300 → 商家退款 100 → 返还 100 → 撤销商家退款 → 补付 100 → 撤销返还确认。此时 B 多付 100 元。JSON 与服务器导出、流式上传的 ZIP 都能恢复，成员余额、流水条数和历史条数一致。再补备注留下多付历史并返还结清后，两种恢复仍通过。比较成员按姓名对应，不依赖数据库返回顺序或恢复后的新 ID。

### 实际 DOM 与受控请求顺序

- 预算保存成功/失败 × 分类/币种/概览历史切换/页面往返后新日期输入，共八条场景。成功后移除保存表单并恢复自动同步，失败后保留 2000 元输入并启用核实；往返后的日期节点、值和焦点不变，写入各一次。
- 批量返还 40 元和全额 100 元响应丢失后关闭重开；全额结清仍能找到核实入口。三个领域账号读取一致，返还仅记录一次。
- 使用新的模块实例模拟标签页重载，待核实批量请求从 sessionStorage 恢复原金额、分配、版本和键；账号、账本和付款方向相互隔离。
- 不匹配有效流水的当前金额、历史中超出已记录转账的金额仍被恢复校验拒绝。现有退款超额和无效撤销校验回归继续通过。

## 证据边界

断网通过请求前异常或真实数据库提交后丢弃响应模拟，没有物理断网。页面交互使用 jsdom 和实际应用函数/DOM 事件；未将其称为真实浏览器或手机验收。本轮没有新增真机软键盘、系统文件选择器、视觉检查或公开部署验证。测试说明仅在文档与对话中，不加入产品界面。
