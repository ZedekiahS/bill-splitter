# 待核实入口与预算旧响应

基于 `5c6459e` 最新复核中的两项问题。本轮不增加功能范围。

## 修复

- **待核实入口**：从当前账号、当前账本保存的批量请求枚举入口，同时读取内存及 sessionStorage，不依赖当前欠款方向或付款流水。余额归零不会清除未知结果；关闭重开、标签页重载仍使用原载荷与原键。服务端明确返回冲突后，结束待核实状态并移除当前页面上的对应入口，避免留下失效按钮。
- **预算旧响应**：以月份、币种为键合并预算，保留较高版本；旧数组遗漏的其他月份/币种不会消失。移除预算的 `amountCents=null` 仍保留版本，零预算也正常处理。保存完成释放 busy、恢复表单，与是否接受旧数据分开处理。保存及重新读取不再先用旧数组覆盖原数据对象；当前报告回调同样执行版本合并。
- 延续局部刷新预算区域，保留报告日期输入节点、值、焦点、编辑标记及阅读位置。账号退出后的配置隔离未改变。

## 回归证据

原实现下先运行新增测试：待核实入口遗漏 1 项、旧预算响应 6 项（新预算/移除/零预算 × 有无未提交日期）均失败；修复后通过。随后还补上明确冲突后的可见入口清理测试，先失败再修复。

- **308 项本地测试通过**（`npm test`）。
- **75 项真实 PostgreSQL/API 测试通过**。使用隔离 schema 和虚构账号，测试 schema 已移除，测试 PostgreSQL 已停止，未修改真实账本。
- 三个账号、实际批量窗口函数及 DOM 事件、API 客户端和真实数据库：900 元三人账单已还清 → 商家退 300 元 → B 核实收到 40 元前请求发送失败 → A 撤销商家退款 → 三人账目确认 A→B 欠款为零且无该方向流水 → B 重开仍有核实入口 → 原键原载荷返回 409 → 不新增付款，清除待核实状态。
- 新模块实例模拟标签页重载，从 sessionStorage 直接发现待核实请求；无需提供任何欠款或付款方向。其他账号、其他账本均不显示该请求，核实成功后不再列出。
- 预算使用同账号的两个真实登录会话：会话 A 保存 2000 元版本 1，获取真实报告后延迟交付；会话 B 分别更新为 1000 元、移除预算或零预算（版本 2）。报告重新挂载并显示新数据后，输入尚未提交的日期，再释放旧响应。当前卡片保持版本 2，写入一次，日期节点、值、焦点和编辑标记保持，另一账号的预算不受影响。
- 实际 app/HTML、hash 导航及自动同步调度器补测：上述三种新状态各覆盖有/无未提交日期，旧响应到达后立即检查金额未回退，再检查三轮同步。保留其他月份、币种的数据及其版本，编辑预算使用当前版本 2。
- 同一报告数据对象收到旧保存响应时也保留较新预算，防止仅在当前挂载回调中比较版本、却提前覆盖原对象的遗漏。

## 边界

网络故障通过发送前异常注入，旧响应通过控制真实读取结果的交付顺序模拟；不是物理断网。页面测试使用实际应用函数和 jsdom DOM，未冒称真机、真实浏览器弱网或视觉验收。本轮未公开部署。客户页面没有加入开发/测试说明。
